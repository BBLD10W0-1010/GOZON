# Домашнее задание по модулю "Тестирование и конкурентность"

Домашнее задание выполняется поверх результата `hw1` (сервисы `product-service` и `cart`).
Необходимо покрыть их тестами и сделать потокобезопасными.

## Основное задание

### Часть 1. Тесты

#### Юнит-тесты

Покройте бизнес-логику обоих сервисов юнит-тестами. Нужно так же продемонстрировать навыки тест дизайна, самостоятельно придумав тесткейсы.

Требования к юнит-тестам:

1. Используем `testify/require`;
2. Минимальная цикломатическая сложность.
3. Каждый кейс получает чистый инстанс сервиса — общий инстанс между кейсами запрещён.
4. Коды gRPC-ошибок сравниваем через `status.Code(err)`, а не по тексту сообщения.
5. `t.Parallel()` на родителе и в каждом подтесте.

#### Интеграционный тест

1. Тесты лежат в отдельном пакете (например, `test/`) и являются чёрным ящиком:
   импортируется только сгенерированный gRPC-контракт `product-service`, про внутренности
   сервисов тест ничего не знает.
2. Тест **не поднимает сервисы сам** — ходит в запущенные `make run-all` (gRPC `:50051`,
   HTTP `:8080`). Соединение — в отдельном файле-помощнике, сценарий — в `_test.go`.
3. Тест идемпотентен: не полагается на накопленное состояние живых сервисов
   (id, счётчики, содержимое корзин других запусков).
4. Проверяется и happy path, и коды ошибок — через настоящий сетевой хоп.

### Часть 2. Конкурентность

1. **Потокобезопасная корзина.** Состояние `cart` (корзины пользователей) читается и
   пишется из параллельных HTTP-запросов. Защитите его:
   - доступ к корзинам — под `sync.RWMutex` (чтение содержимого корзины — `RLock`,
     добавление товара — `Lock`);
   - счётчики/значения, которые инкрементируются одной операцией, — `atomic`;
   - после фикса `make test-race` зелёный.
2. **Параллельное получение товаров.** При чтении корзины (`GET /user/<user_id>/cart`)
   сервис `cart` запрашивает информацию о каждом товаре в `product-service` (`GetProduct`)
   параллельно:
   - на каждый SKU — своя горутина, ожидание всех — через `sync.WaitGroup`
     (допустимо `errgroup`);
   - результаты складываются в заранее выделенный срез по индексу горутины —
     так запись не требует мьютекса;
   - на всю пачку запросов — общий таймаут (`context.WithTimeout`); исходящие gRPC-запросы
     без таймаута запрещены;
   - если корзина пуста — обращения в `product-service` не делаем;
   - обработка ошибки одного из запросов (например, товар исчез из `product-service`) —
     по аналогии с добавлением: 412, ответ не отдаётся частично.

## Дополнительное задание

1. **REST-тест**: через `httptest` (или интеграционно, по HTTP на `:8080`) проверить
   контракт `GET /user/<user_id>/cart`: состав и порядок `items`, `total_price`,
   типы полей в JSON (`sku` — число, цены — числа).
2. **Тестируемый main**: вынести поднятие серверов из `main.go` в функции, принимающие
   listener, — чтобы точку входа можно было покрыть тестом.
3. **Бенчмарки**: `BenchmarkGetProduct` в `product-service`, `BenchmarkAddToCart` и
   `BenchmarkGetCart` в `cart`. Сетап (создание сервиса, предзаполнение корзины) не должен
   попадать в измерение; запуск с аллокациями (`-benchmem`); ошибочный запрос в бенчмарке —
   `b.Fatal`, а не тихий повтор.
4. **Цена синхронизации**: снять `make bench` до и после добавления `RWMutex`;
   полученные цифры (ns/op, allocs/op) привести в README или описании MR.
5. **Тестовый двойник для `cart`**: логика `cart` тестируется без реального gRPC-вызова —
   подставьте fake/stub, реализующий клиентский интерфейс `product-service`, — включая
   сценарий "товар не найден" (для проверки ответа 412).
6. **Race-тест**: N горутин одновременно добавляют товары в корзину одного пользователя
   (и/или в `product-service` — в общую map), `sync.WaitGroup` для ожидания. Файл под
   билд-тегом `//go:build race`: обычный `make test` его не компилирует, под `-race` тест
   существует и **обязан** пройти после фикса. Порядок работы: сначала тест → убедиться,
   что под `-race` он ловит DATA RACE на несинхронизированной map → починить (часть 2) →
   убедиться, что стал зелёным.

## Makefile

Добавить к целям из `hw1`:

- `test` — все юнит-тесты (`go test ./...`); api-тест (и race-тест из допзадания) при обычном
  запуске не видны;
- `test-race` — все тесты под race-детектором (`go test -race ./...`) — должен быть зелёным;
- `test-api` — интеграционные тесты против запущенных сервисов
  (`go test -v -count=1 -tags=api ./test/`); `-count=1` обязателен — кэш результатов
  для тестов против живого сервиса врёт.

## Ожидаемый результат

- `make test` — зелёный; интеграционный тест (тег `api`) в обычный прогон не попадает;
- `make test-race` — зелёный;
- `make run-all` + `make test-api` — интеграционный тест PASS;
- параллельные запросы к `cart` не теряют и не портят данные;
- `GET /user/<user_id>/cart` с несколькими товарами запрашивает их описания в
  `product-service` параллельно (по горутине на SKU, с общим таймаутом).
