# HM3 - тестирование и конкурентность

Отдельная копия сервисов из HM2. В тексте задания основа названа `hw1`,
но в этом репозитории `product-service` и `cart` находятся в HM2.
Условие сохранено в [Homework_3.md](Homework_3.md).

## Запуск и проверка

Нужны Go 1.26+, GNU Make и `sh`. Все команды выполняются из папки HM3.

```sh
make test
make test-race
```

Для `-race` нужен включённый cgo и C-компилятор. В Windows подойдёт
w64devkit: его папка `bin` должна быть в `PATH`, а `CGO_ENABLED=1`.
Требования к компилятору описаны в [документации Go](https://go.dev/doc/articles/race_detector#Requirements).

В первом терминале запустите сервисы:

```sh
make run-all
```

Во втором терминале выполните:

```sh
make test-api
```

Каталог слушает gRPC на `:50051`, корзина - HTTP на `:8080`.
В `products.json` есть три товара. Корзины хранятся в памяти и теряются при
перезапуске. Остановка `make run-all` через Ctrl+C завершает оба процесса.
Собранные программы остаются в `bin/`, этот каталог исключён из Git.

| Цель | Что делает |
| --- | --- |
| `test` | `go test ./...`, без файлов с тегами `api` и `race` |
| `test-race` | `go test -race ./...`, включая проверку конкурентных HTTP-запросов |
| `test-api` | `go test -v -count=1 -tags=api ./test/` против живых сервисов |
| `bench` | Три прогона бенчмарков с `-benchmem`, без запуска тестов |
| `generate` | Генерация Go-контракта через `protoc` |

Сгенерированные файлы включены в проект. `protoc` и его Go-плагины нужны
только для изменения контракта.

## Что изменилось

Бизнес-логика корзины находится в `internal/cart/service.go`, HTTP-слой
разбирает запросы и преобразует ошибки в коды ответа. В юнит-тестах вместо
gRPC-клиента используется stub с тем же интерфейсом. Каждый кейс создаёт
свой сервис; родительские тесты и подтесты используют `t.Parallel()`.
Проверки написаны через `testify/require`, gRPC-коды сравниваются через
`status.Code(err)`.

Карта корзин и её содержимое защищены `sync.RWMutex`. Добавление изменяет
количество и сохранённую сумму под одной блокировкой. Отдельные atomic-операции
для этих двух полей нарушили бы согласованность проверки переполнения.
Независимый счётчик HTTP-запросов для `request_id` в логах использует `atomic.Uint64`.
Каталог после запуска не меняется; `NewServer` копирует входную карту.

GET копирует содержимое корзины под `RLock`, затем обращается к каталогу
после снятия блокировки. На каждый SKU создаётся горутина, результаты и ошибки
пишутся по своему индексу в заранее выделенные срезы. `sync.WaitGroup` ожидает
все ответы. На всю пачку действует один `context.WithTimeout` в 3 секунды;
POST также всегда задаёт таймаут для gRPC.

GET возвращает актуальные названия и цены из каталога, товары отсортированы
по SKU. Пустая корзина даёт 404 без запросов к каталогу. Если товар исчез,
возвращается 412; недоступность каталога и переполнение суммы дают 500.
Частичный JSON с товарами при ошибке не отправляется.

В `cmd/cart/run.go` и `cmd/product-service/run.go` запуск вынесен в функции
`run`, принимающие listener и context. Отдельные тесты проверяют реальные
серверы на свободных портах, остановку и ошибку закрытого listener.

## Тестовые сценарии

- Каталог: существующий и неизвестный SKU, неположительные SKU, пагинация,
  пустой каталог, повреждённый JSON, некорректные поля и изоляция данных.
- Корзина: повторное добавление, независимость пользователей, валидация,
  переполнение, отмена запроса, ошибки и некорректные ответы каталога.
- Параллельный GET: барьер в stub требует одновременного входа всех запросов.
  Проверяется общий deadline, обновление цены, исчезнувший товар и отсутствие
  частичного результата.
- REST: состав корзины, сортировка, сумма, числовые типы JSON и коды ошибок.
- Race-тест: 16 горутин одновременно выполняют по 20 добавлений и чтений
  корзины одного пользователя. Итоговое количество должно быть 321.

`test/client.go` содержит только соединения и вспомогательные функции для API-тестов.
Сценарии лежат в `test/api_test.go`, оба файла закрыты тегом `api`.
Из проекта импортируется только сгенерированный protobuf-контракт.
API-тесты не поднимают процессы, получают SKU через gRPC и выбирают случайные
положительные userID. Для happy path в каталоге должно быть хотя бы два товара.
Два последовательных запуска `make test-api` проверены без перезапуска сервисов.

## Гонка и замеры

Сначала новый race-тест был запущен на варианте HM3 без блокировки:

```sh
go test -race -run TestConcurrentCartRequests -count=1 ./internal/cart
```

Детектор сообщил `WARNING: DATA RACE` между чтением карты и `AddToCart`.
После добавления `RWMutex` тот же тест и полный `make test-race` прошли.
В исходном HM2 мьютекс уже был; для сравнения использовалась новая реализация
HM3 до добавления в неё блокировок, а не замеры разных алгоритмов.

Замеры выполнены 26.10.2026: Go 1.27.2, Windows amd64,
Intel Core i3-12100, `GOMAXPROCS=8`, без `-race`.
Ниже медианы трёх прогонов `make bench`:

| Бенчмарк | Без RWMutex, ns/op | С RWMutex, ns/op | allocs/op до / после |
| --- | ---: | ---: | ---: |
| GetProduct | 26.85 | 29.94 | 1 / 1 |
| AddToCart | 380.6 | 440.4 | 6 / 6 |
| GetCart | 3236 | 3521 | 21 / 21 |

Исходный вывод: [до](docs/bench-before.txt), [после](docs/bench-after.txt).
GetProduct не менялся и служит контрольным замером: его разброс показывает,
что разницу времени нельзя целиком приписать блокировкам.
Число аллокаций после синхронизации не выросло.

Создание сервисов и заполнение корзины выполняются до измерения.
AddToCart использует бесплатный товар, чтобы сумма не переполнялась при большом
числе итераций. GetCart читает три SKU. Ошибка в бенчмарке завершает его через `b.Fatal`.

## API и настройки

```sh
curl -X POST http://localhost:8080/user/1007/cart/2958025 \
  -H 'Content-Type: application/json' -d '{"count":2}'
curl http://localhost:8080/user/1007/cart
```

Swagger UI: `http://localhost:8080/swagger/`, контракт: `/swagger.json`.
Файлы интерфейса Swagger загружаются с CDN.

| Переменная | По умолчанию |
| --- | --- |
| `PRODUCTS_FILE` | `products.json` |
| `PRODUCT_GRPC_ADDR` | `:50051` |
| `PRODUCT_GRPC_TARGET` | `localhost:50051` |
| `CART_HTTP_ADDR` | `:8080` |
| `CART_HTTP_URL` (API-тесты) | `http://localhost:8080` |
